# Changelog

All notable changes to this integration are documented here.

## v3.2.0

### Added
- **Adding an event starts by asking what kind of event it is** – 🎂 *a yearly date for someone*, ⏳ *a one-time event*, or 🗓️ *a custom event*. The form after it then carries only the fields that kind can actually use: the seven yearly types (birthday, anniversary, name day, wedding anniversary, memorial, pet birthday, work anniversary) get no **End date** and no recurrence rule; a one-time event gets its **End date** and a **Year** that is simply required, marked as such by Home Assistant’s own asterisk; a custom event gets the recurrence rule above and no end date. Every label lost the clause explaining which types it did not apply to – *Year (leave empty if unknown; required for one-time events)* is now *Year (leave empty if unknown)* or, where it is required, just *Year* – because the field is no longer on a form where the exception could arise. A config-flow form cannot show one field conditionally on another, and the event type is a field, which is why one form had to carry all of them until now. Editing an event skips the question: it has already chosen its kind, so **Configure** opens its own form directly. The one thing this gives up is changing an event from one kind into another – a birthday into a one-time event, say; the type dropdown now offers that kind’s types only. Delete and re-add for that, which is what such a change amounts to anyway.
- **A custom event can be given a rule instead of a day** – *the first Sunday in September*. Some dates are not a date: Mother’s Day is the second Sunday in May, so it is 10 May one year and 9 May the next, and Father’s Day in Australia is the first Sunday in September. Days like these are observances rather than public holidays, so the database behind *Importing public holidays* mostly does not carry them, and a fixed day and month would be right in one year and wrong in every other. The custom event’s own form carries two more fields for it: **Repeats on the** (*First*, *Second*, *Third*, *Fourth* or *Last*) and the **…weekday of the month**. Together with the **Month** above them, that is the whole rule – there is nothing else to fill in. Leaving both empty, which is how the form opens, keeps the plain day and month the event has always had, so nothing changes for a custom event that does not want one. They are on that form and on no other: every other type is one particular person’s own date, and a birthday happens on the day it happened, not on the second Sunday of anything. The two fields go together – setting one and not the other is refused rather than half-applied – and while a rule is set the **Day** field is not read, but is left exactly as typed, so clearing the rule puts the event back on that date. There is no *Fifth*: three months in four have no fifth Sunday, so it would be a choice that quietly produces nothing in most years, and **Last** is what anyone reaching for it means – *last Monday in May* being the fourth Monday in some years and the fifth in others. The sensor reports where the rule landed in `next_date` as it does for every event, and carries the rule itself as the new `weekday` (Monday = 0) and `nth` (`-1` for last) attributes, absent on every event without one. Requested in [#9](https://github.com/somansch/annuals/issues/9) by [@craigmate](https://github.com/craigmate).
- **The CSV file carries the rule too** – two new columns, `nth` and `weekday`, at the end of the row where `end_date` already is, so a file written by an older version still imports unchanged and an exported file still re-imports as what it was. Both together and on `custom` rows only; a row that sets one, or sets them on any other type, names its own line number and is skipped, like every other bad row. The columns are also what *Export events to CSV* writes now, and `end_date` – there since multi-day events arrived – is documented in the README’s column table at last.
- **What an event type’s colour paints is set inside its block now, not beside its name.** The switches – *Icon*, *Accent bar* and *Whole row* in the list, *Entry text* in the timeline – used to ride on the type’s own heading line, where they sat wherever that name happened to end and said nothing about what they did. They lead the block instead, as rows of their own: switching one on brings its own colour row up directly underneath it, which is where you were about to look. Each carries its own **i**: “Color this type’s icon”, “Color the whole row, its text included”, and so on. The heading is left as a name and a chevron. Same for every embedded calendar, which carries the same switches.
- **Multi-day events reaches an embedded calendar’s own entries.** *Multi-day events* (Settings → Events) has only ever governed a one-time event with an end date; a calendar entry covering a week was one row on the day it began, whatever the setting said. It now governs both: **Only the first day**, **Only the last day**, **First and last day** or **Every day** apply to a holiday in a shared family calendar exactly as they do to a trip entered in Annuals, and every row says which part it is – *Ski trip (start)*, *(end)*, *(day 3)*. An all-day entry is read the way Home Assistant reports it, whose end is the morning after, so a Monday-to-Friday entry is five days rather than six; a timed one counts the days it actually touches, keeps its start time on the first row and its end time on the last, and one ending at midnight still belongs to the day before. An ordinary appointment is untouched. Two things came with it: the setting no longer waits on **One-time event** being among the card’s types – an embedded calendar is reason enough to show it – and the part is written on both of an event’s names, so the **Timeline** layout tells the days of one trip apart too, which it never did even for a one-time event.
- **The card editor’s Design and Highlight tabs fold** – one line per thing you can set, and only the one you open shows its settings. Rows for a dozen elements stacked was a wall to scroll past to reach the last of them; folded, each tab reads as a list of what can be styled. On **Design** that is every element – card title, the row’s own columns, and in the Timeline layout its header, tooltip, list, button and two lines – and every entry under **Event types** and **Embedded calendars** below them. On **Highlight** it is each badge and each of Past / Today / Soon. Four lists in all, each its own accordion, since opening a type has no business folding away the element being worked on above it. Opening one closes the previous, the way the two sections above the tabs already behave, and every line works from the keyboard as well as the mouse. What sits *on* such a line still does its own job: a badge’s switch switches the badge, its two placement switches place it, and the **i** reads its tooltip – none of them folds the block away underneath the cursor. Switching a badge on opens it, since what was just enabled is exactly what would otherwise be folded away. A group of names – the Date block’s three lines, an embedded calendar’s fields – opens as a whole, being one thing to style. This is the shape the [blitzer](https://github.com/somansch/blitzer) card’s editor already had.
- **The list can fold, and a card can be one row tall.** Two settings that go together. **Fold the rest away** (Layout → List view) shows only the first few events and puts the rest behind a chevron, with **Events shown** saying how many stand before it – three unless you say otherwise. The rest are not built at all until the chevron is tapped, so a long list behind the fold costs nothing, and the chevron sits below the list rather than in it, staying put while the list scrolls under it. Tapping it is a look, not a setting: it is not written to the dashboard, so unfolding a card does not unfold it for everyone else. List layout only – the timeline already has its own **Details** under the axis, and two expanders on one card would be two answers to the same question. Switching the fold off takes its count with it rather than leaving a number in the YAML that nothing reads.

  The sizing floor came down with it: a card may now be given **one** row instead of two, which is what a card showing a single date wants. One row is 56px, and what fits in it is worth knowing: an ordinary row is 45px and the card’s usual edges another 32, so 77px in all - more than a single row holds, and the list scrolls. Compact with a couple of columns comes to 46px and fits as it is; anything else wants *Minimal* below. Above one row the list simply shows what fits and scrolls or folds the rest, as before.

- **Minimal (one row, tight edges)**, under *Compact* in Layout → List view. A card given a single grid row still grew a scrollbar, and the card’s own edges were why: measured with a compact row in a 56px card, 16px above and below leave 24px for a row that needs 36, so the row was cut and the list scrolled. This trims them to 6px and the row’s own vertical padding to 2px. Both are needed: edges alone left a row with an **icon** column at 42px in exactly 42px of space, fitting on the pixel and tipping back into a scrollbar at the slightest rounding - with the row tightened too it is 34px in 42px, so an icon is usable here rather than merely arithmetic. The sides keep 12px, since width was never the problem and text against a rounded corner reads badly. The row also sits in the middle of whatever height is left instead of against the top edge, so a one-row card given more than one row of space no longer hangs its single line from the ceiling - and where the list does overflow, it falls back to aligning at the top rather than centering its first row out of reach. Offered only while *Compact* is on, since it is the compact row that is short enough for tight edges to be worth anything, and switched off together with it rather than staying on with no switch in sight. Its “i” says what it is for: a card showing one event. With more, the rest is cut off or has to be scrolled, exactly as before.

- **The card takes the size a sections view gives it.** Home Assistant's **Layout** tab used to open with *"This card does not fully support resizing yet"*, and it was right: handed a height, the card drew its own instead - measured, 644px whether it was given 700 (a gap left below it) or 200 (444px of it lying over whatever came next). It now fills exactly what it is given, and the event list takes what the title leaves and scrolls, so a card made shorter shows fewer events rather than overflowing. The notice is gone and the real controls are offered in its place: both sliders, **Auto height**, **Full width** and **Precise mode**. Height still follows the content until a row count is pinned, because that is what this card is - a list as long as the events in it. The floor is two rows, and six columns of twelve for the list layout: measured, below about 240px its rows start overflowing their own width and names wrap until the card is twice as tall. The **Timeline** asks for four, being a single horizontal axis that holds together much narrower - measured unchanged down to 180px. Its tooltip moved with all this: it was kept inside the card, and is now kept inside the scrolling list, which is the tighter of the two - measured on a real card, ha-card 174-320 against a list of 191-303, so leaving it clamped to the card would have cut it off by 13px at either end.
- **Slovak joins the languages, and everything here is translated in all sixteen** – the menu and its three answers, all nine forms, the two rule fields and their dropdowns, and the one error the rule can raise. Checked against what Home Assistant itself resolves rather than against the files: 348 strings per language, none falling back to English. **Slovenčina** is new, from the draft in [#8](https://github.com/somansch/annuals/pull/8) – the card’s 485 strings and the integration’s own, brought up to this release and aligned with the other fifteen (its holiday categories gained the plural forms the editor’s filter grid needs, and the integration keeps its own name rather than being renamed in Slovak alone). And the **holiday translations** screens went with all of it – that whole branch of the hub menu, its import screen and both of its result messages had been English-only since they arrived.

### Fixed
- **The card sometimes never appeared, until the page was reloaded.** Home Assistant loads a bundled card by writing a bare `import()` for it into the page it serves. That import is awaited by nothing, caught by nothing, and made **exactly once per page** - measured: one request, and moving between dashboards never makes another, because that is an in-app navigation and the document stays. So a single fetch that did not arrive - Home Assistant restarting in that moment, a proxy hiccup, a phone losing the network while the page was building - left the card missing for as long as that page stayed open, however healthy the server got a second later. Only a reload cured it. Worse, the browser remembers a failed import per URL: measured, a second import of the same address, with the file back and answering `200`, failed again without sending a single request. What Home Assistant is handed now is `annuals-card-loader.js`, a few hundred bytes whose own fetch can hardly fail, and it fetches `annuals-card.js` itself - backing off 1, 2, 5, 10, 20, 30 seconds, under a fresh address each time, and trying again whenever the tab is brought back to the front or the browser comes back online. Nothing needs reloading when an attempt gets through: Home Assistant watches for the element being defined and rebuilds the card where it had shown “custom element doesn’t exist” - measured, the card appeared sixteen seconds after the file came back, in the same page. Reported in [#10](https://github.com/somansch/annuals/issues/10).
- **A card that is not on disk no longer takes the whole integration down.** Reading the card file’s own date was the first thing setup did, so an incomplete download - the realistic way to end up without it - meant no events, no calendars and no services, over a dashboard card. Setup now says so once, by name, in the log, and carries on with everything else. Measured with the file removed: 146 entries, all loaded, 145 sensors, 10 calendars and both services up, and one warning naming the file. If the loader is the file that is missing, the card itself is handed over instead: a card that cannot retry still beats no card at all.
- **Re-importing public holidays no longer duplicates the ones the `holidays` library has renamed.** A holiday is identified by its name in that library’s own default language, and the library rewrites those names from time to time – sometimes changing nothing but a capital letter. Measured on the Netherlands across two releases: five of the ten public holidays changed that way, *Eerste kerstdag* becoming *Eerste Kerstdag*, *Goede vrijdag* becoming *Goede Vrijdag*, and three more. The identity compared those names exactly, so after such a release **Import public holidays** stopped recognising the entries already there and added a second one beside each – the same holiday twice, one capital letter apart. It ignores case now, and the holiday names you write yourself are matched the same way, so a translations file exported before such a release still applies afterwards.
- **One entry per holiday, whatever categories it was imported under.** The library files the same date under several categories at once – a US statutory holiday is typically both *public* and *government* – and often under a different name in each: *Washington’s Birthday* as government, *Washington and Lincoln Day* as public, so only the date says they are the same day. Importing those categories together always collapsed them; importing them one after the other did not, and left the holiday standing twice. Now it is folded either way, and **public wins**: a public holiday replaces any other category on its date, a non-public import is skipped where something already speaks for that date, and between two non-public ones the older stays. Measured: with US *government* already imported, importing *public* removed the ten government entries it superseded and kept ten public ones; the other way round, importing *government* into an instance that already had *public* reported *0 queued* instead of adding twelve. Whatever was already on disk is folded the same way at the first start after updating. Multi-day school breaks stay out of it – a break’s first day sharing a date with Christmas Eve must not let the single day swallow the whole break – and so does a holiday’s *(observed)* variant, which is deliberately its own entry.
- **The duplicates already on disk are cleaned up once, at the first start after updating.** Where two entries turn out to be one holiday, the spelling with the capitals is kept – that is what the library settled on, and what a fresh import produces – and the other is removed after handing over any holiday names you had typed into it, so nothing you wrote is lost. Each removal names both entries in the log. Measured on a copy of a real instance: 16 Dutch entries went to 11, only the capitalised spellings left, the typed translations carried across, and a re-import then reported *11 holidays, 0 new, 11 updated* instead of adding another eleven. A holiday the library itself spells in lower case – *Eerste paasdag* – keeps that spelling; there is nothing to choose between where only one version exists.

**If you already automate on holidays, two things move with that cleanup.** A holiday that stood as *government* and as *public* now stands only as *public*, so a reminder automation filtering on a secondary category – the Annuals blueprint’s **Holiday categories**, or your own `category` condition – can go quiet for days it used to fire on. Filter on *Public* instead, or drop the filter. And where an automation names holiday entities one by one rather than by type, the absorbed entry’s `sensor.annuals_…` is gone; Home Assistant shows it as unavailable in the picker, and picking the surviving entry restores it. Nothing else moves: an automation that targets by event type, or that never mentions holidays, carries on exactly as before.

The rule above changes nothing about **importing public holidays**: Thanksgiving, Memorial Day, Labor Day and every other “nth weekday” public holiday already resolve themselves per year from the holidays database, exactly as before. The rule is for the observances that database does not carry, on events you enter yourself. What *did* change about importing them is under *Fixed*.

## v3.1.0

### Added
- **A separator line can name the boundary it marks** (List view → Day/Week/Month separators). Each of the three gains a switch of its own – **Show weekday**, **Show calendar week**, **Show month** – that writes that boundary’s own name on the rule itself, in the card’s language: centered, on a plate with strongly rounded corners in the card’s background color, so the line breaks around the text instead of running through it. The plate follows the text’s own width, so “Monday” and “9” each leave exactly the gap they need. Switching it on reveals the label’s own appearance, laid out like any Design block: **Label color** and **Label background**, empty meaning the theme’s own text color and the card’s own background – which is what makes the plate read as a gap rather than as a shape – then **Font** with Bold/Italic/UPPERCASE/Underline and **Letter spacing**, empty meaning 0.75em relative to the card’s own font size. Each scale is set on its own, so a card can run a bold orange week number over a plain grey weekday. The week number is counted from the same **First day of the week** that decides where the week lines fall, so a line and the number on it can never disagree – with a Monday start that is ISO-8601 week numbering. All three are off, so a card with separators already on is unchanged.
- **Event status reaches the Timeline layout** - the status blocks used to hold list-only settings, so in the Timeline they showed nothing but an animation. They now carry the same three the event types do there: **Entry text color**, **Icon color** and **Icon animation**, built and switched exactly like their list counterparts. No *Background color* - the timeline has no row to tint - and no *Accent bar color*, for the same reason. *Entry text color* shares its switch with the list's *Whole text color*; only one of the two is ever on screen. A status can colour the timeline's glyphs too - Today's dot and its header and Details-list icons - but that is a switch of its own, off everywhere to start with: the timeline has only ever coloured those from the event type, and the list's switch (on for Today and Soon) must not decide for it. So an untouched timeline card is unchanged.
- **Every event type styles each target on its own** - a type used to carry one color that its switches then pointed at the icon, the bar or the row. Each target now has a color row of its own under the type: **Whole row color**, **Accent bar color** and **Icon color** in the list, **Entry text color** and **Icon color** in the timeline, plus an **Icon animation** behind a switch. Each row appears only once its own switch is on - the icon's is always there in the timeline, which draws a glyph for every event - and each is empty by default, meaning "the type's own color", which is the single value they all shared before. So nothing changes until one is filled in; each field's swatch previews that color, so an untouched row shows what it will actually render as. The type's own color has no row of its own any more: the four below it are what is set now, and with **Design rows by event type** switched off the whole section collapses to that one switch. Embedded calendars have the same block. The section's own switch is **Design rows by event type** now, since it is no longer only about color.
- **The icon animation follows the same chain the colors do** - the **Icon** block in Design sets one animation for every icon on the card, each **event type** can override it with one of its own (a new *Icon animation* row under its color), and so can each **embedded calendar**, under the same row in *Embedded calendars*, and a **status** overrides both, the way *Color rows by event type* and the status blocks already work for color. All three apply in the list and the timeline alike. Nothing is stored until it differs from the default, and an untouched card is unchanged.
- **Event types and embedded calendars show their own icon** - each row under *Event types* and *Embedded calendars* in Design now leads with the icon that type actually renders with, taken from the first of your own events of that type, and each calendar with the icon Home Assistant holds for it. Sized off the label's own text rather than a fixed value, and sitting on the text's baseline, so the name and its icon read as one line.
- **The Timeline gets a target switch of its own** - the three switches beside an event type (*Icon*, *Accent bar*, *Whole row*) paint things the timeline does not have, so in that layout they give way to **Entry text**: the dot always carries the type's color, and this decides whether the event's own text carries it too - both the header sentence at the top and its line in the list under the axis. Off by default, so nothing changes until it is set, and it is stored per type and per calendar like the other three.
- **The row's default icon color and animation live with the Icon column** - Layout → **Design** gains an **Icon** block, listed in the row columns' own order like every other element and shown only while that column is in use. Its *Color* and *Animation* are what every status falls back to. *Fixed icon color for all icons* is gone with it: it did the same job from a second place, and a card that had it set carries the value over as this default. The per-status *Show icon* switches are gone from the editor too - the card still honours a card that had one switched off, but there is no longer a control for it.
- **Highlight is three status blocks instead of two overlapping lists** - the tab used to hold a *Past/Today/Soon* list for background tints and a separate *Default/Today/Soon* list for icon colors and animations, each missing exactly the entry the other had. It is now one **Event status** section with a block per status - **Past events**, **Today**, **Soon** - each built the same way: **Background color**, **Accent bar color**, **Icon color**, **Icon animation**. There is no Default block: the defaults are the Icon column's and the Accent bar's own Design blocks, which is where the rest of a column's styling already lives. Each of the last three settings carries a plain on/off switch of its own, shaped like the background tint's: off, the setting folds away and the row takes what applies otherwise - the event type's color where *Color rows by event type* is on, the Design default where it is not; on, this status' own value wins and the field below sets it. The switch carries no label of its own, the row's own tooltip explains it. A fourth, **Whole text color**, sits right under *Background color* and covers everything in the row except the icon and the accent bar, which have colors of their own. It is a color field rather than a plain switch: with a pink icon and a blue bar there is no sensible colour to borrow for the text, so it gets one. Left empty it takes the status' own color, which is what the switch it replaced used; off, the row takes whatever else applies - the event type's color while *Color rows by event type* is on, otherwise the Design default. Today and Soon start with their color settings overridden, which is what makes them stand out; their **Icon animation** does not, since every animation starts at *None* and an open field that changes nothing is just a row in the way - a card that had actually picked an animation for Today or Soon keeps it, switched on by the reading. Past overrides nothing, because past rows used to be ordinary rows in every respect. So no existing card changes appearance. Icon and Accent bar settings appear only while their column is in the row columns.
- **The accent bar can take a color per status** - *Accent bar color* in each status block. Left empty the bar keeps following that status' icon color, which is the only thing it could be before, so nothing changes until it is set; filled in, a card can run a red bar next to a monochrome icon for Today alone. The Accent bar's own *Color* in Design still overrules all four, the way *Fixed icon color for all icons* overrules every icon.
- **The Highlight tab opens with a BADGES section** - VIP, Important and to-dos used to sit below the by-date Past/Today/Soon rows, although they mark a property of the event itself rather than how near it is. They now come first, under a heading of their own, and Past/Today/Soon keep the *Highlight* heading below them. No setting changed, only where it is.
- **Each badge chooses where it is drawn** - two switches beside every badge's own switch in Layout → Highlight → Badges, in the same place the EVENT TYPES rows keep theirs: **Event icon** puts the badge in the corner of the row's event icon, where all three have always been, and **Accent bar** puts it in a stack immediately left of that column, centered against the row and always ordered VIP, Important, to-do from the top. They are independent, so a card can move the to-do badge to the bar and leave VIP and Important on the icon, or run one badge in both places. Switching the last one off switches the badge itself off and folds its settings away with it - a badge that is shown but drawn nowhere is a state with nothing to show for it - and switching either placement back on brings it back. Turning the badge on from its own switch while both placements are off returns it to where badges start, the event icon. Useful on a card that shows no icons at all, or one that wants the flags read as a column of their own rather than as decoration on something else. The stack keeps a badge's width whether it holds three badges or none, so every row's bar stays on the same vertical line, and a row with nothing on the bar renders the bar alone with no gap. Both switches appear only while **both** the Icon and the Accent bar column are in the row columns, because only then is there a placement to choose: with one of them the remaining switch would just be the badge's own on/off switch a second time. With one column the badge goes there whichever target is stored, so taking a column out of the row never makes a badge disappear and putting it back restores what was configured. With neither - the *Minimal* preset, say - the whole **Badges** section is gone from the list layout: there is nothing in the row for a badge to sit on. The Timeline layout keeps it, since it draws its badges on the dots and on its own header and Details list, which no row column decides. Neither switch appears in the Timeline layout, which draws its badges on the dots.
- **Both halves of a badge can be colored** - each badge is a symbol on a disc, and until now only one of the two was reachable: VIP and Important set the disc and left the symbol white, while the to-do badge set the symbol and left the disc on the card's own background. Every badge now has a **Badge color** for the symbol and a **Badge background color** for the disc. Existing cards render identically - the keys they already carry keep exactly the half they always painted, and the new field is simply empty. The badge icon fields lost their prefix with it: three rows labelled *VIP badge icon*, *Important badge icon* and *To-do badge icon* now read **Badge icon**, since each already sits under its own badge's heading, and *Badge color (List)* is just **Badge color**, the List layout being the only place it shows.
- **The "no events" line can be reworded and styled** - the card's placeholder for an empty list was fixed text in the card's own language and fixed in appearance. **No events text** (Settings → General, right under the card title's *Hide* switch) replaces the wording; left empty it stays the built-in translated phrase, exactly as an empty *Card title* keeps the default one. A field holding only spaces counts as empty rather than blanking the line out. Its appearance gets a block of its own in Layout → **Design**, directly under Card title - color, size, Bold/Italic/Uppercase/Underline and letter spacing, the same shape every other element has. Unset, it renders as it always did, in the theme's secondary text color. Both layouts show the same line, so the block is always listed rather than appearing and disappearing with the row columns.
- **Three one-click starting points for the row columns** (Layout → List view) - **Default**, **Agenda** and **Minimal**, as buttons above the list. *Default* is the arrangement a new card opens with (Icon, Full name + Type, Occurrence, Countdown); *Agenda* leads with the Date block, then Accent bar, Full name + Type, Occurrence and Icon, so the list reads like a paper agenda instead of a table; *Minimal* is Name, Occurrence and Countdown, for a card with room for nothing else. The Agenda arrangement was inspired by [Calendar Card Pro](https://github.com/alexpfau/calendar-card-pro) by [@alexpfau](https://github.com/alexpfau). Each replaces the whole arrangement and stays editable afterward, like any other change to the list, and whichever one matches the list as it stands is highlighted - so the buttons say where the card is, and touching a single column clears the marking. They only ever write the columns - *Compact* remains its own switch, so a preset rendered compactly is a combination you can keep. The paragraph above them lost its list of Custom text placeholders, which had gone out of date and was three lines of reference material in a spot meant for one sentence; the full list is in the README.
- **Each row can take the color of its event type, or of the calendar it came from** (Layout → Design → *Color rows by event type*, off by default). On, a row resolves its own color: **Today** and **Soon** first if their new *Override* switch is on, then the **embedded calendar** it came from, then its **event type**, then Default. What that color paints is set per event type, on three switches in the type's own heading line: **Icon**, **Accent bar** and **Whole row**. Icon and Accent bar start on and Whole row off; *Whole row* colors the row's text too and takes the icon and bar with it, and *Accent bar* only appears while that column is in the row columns. So a card that shows no icons at all still gets per-type colored bars and text - the colors are resolved on the row, not read off the icon. The *Override* switch now covers **Default** as well as Today and Soon, and a status that overrides paints its whole row regardless of the per-type switches; Default starts off, since it covers every ordinary row. Each embedded calendar starts on the color Home Assistant itself stores for that calendar entity, so two calendars are told apart before anything is configured, and gets a row of its own under *Embedded calendars* to override it - with the same three switches, since a row from a calendar belongs to that calendar rather than to one shared type. There is accordingly no *Calendar events* entry among the event types, in either layout; the `type_calendar` key is still read, so a color set by an older version still applies. **Embedded calendars** is listed in the Timeline layout as well, and a calendar's color now reaches its dots there - previously the Timeline drew every embedded calendar in the color Home Assistant stores for it, with only the one shared *Calendar events* entry to override them all at once. The three switches stay out of the Timeline: a dot has no icon, bar and text to tell apart. Icons and bars can each be pinned to one fixed color that ignores all of this — *Fixed icon color for all icons* in the Highlight tab, *Color* in the Accent bar block — for a card that wants colored bars with monochrome icons or the other way round. The per-type colors are the same ones the Timeline colors its dots with, so setting one shows up in both layouts.
- **The editor only shows what the card is actually using** - Design lists the blocks for the row columns that are configured, and nothing else: no Date block rows without a Date block column, no Occurrence rows without the badge, no list-layout fields in the Timeline layout (and no Timeline fields in the list layout). **Card title** appears only while the title is switched on, and the **Accent bar** settings only once that column is in the list. The same applies throughout the rest of the editor: under **Highlight**, each background color, badge icon and badge color appears only while its own switch is on; a category switched off under *Show icon* keeps its heading and that switch and drops its color and animation controls; under **Card background**, the color, image, size and opacity fields appear only after *Show background* is enabled; the **External calendar fields** group waits until an external calendar is actually embedded; and the whole **Timeline** tab collapses to its one-line note about switching the layout style while the card is in the list layout. Two things keep it from hiding something you still need: a field whose value you have actually changed always stays visible, and a `{placeholder}` inside a Custom text column counts as using that field, so `{name} turns {occurrence}` keeps the Name and Occurrence entries. The same reading now covers the card’s data sources as well: an **event type** the *Event types* filter leaves out gets no block under *Design*, since the card can never draw one; **holiday** settings (*Merge observed*, *Merge regions*, the name suffix) wait until holidays are among them; the Timeline’s **Time**, **Location** and **Description** switches wait for an embedded calendar, as the list’s own group already did; and every **to-do** control - *Open to-dos only*, *Complete from card* and the whole to-do badge - waits until a to-do list is embedded. Each keeps the same escape hatch: anything you have actually configured stays on screen, so removing a list or narrowing the type filter never puts a setting out of reach. The switch groups under a row column follow the same rule: **Holidays only** (the name suffix and the type label) waits for holidays among the selected types, and **External calendars only** (*Calendar name*, *Time*, *Location*, *Description*) for an embedded calendar - a column left with neither group loses the indented block altogether. And the **Add** dropdown under the row columns drops the three column types that only ever write an embedded calendar event’s own fields - *Time*, *Location* and *Description* - until a calendar is embedded or the list already holds one of them.
- **Time, Location and Description are styled separately** - the old *Calendar fields* entry set one color and one font for all three at once, plus the source calendar's own name. It is now the **External calendar fields** group in **Design**, laid out like *Date block*: a heading with an indented row per field, so a long description can be made smaller than the time above it, or a location given its own color. All three default to the theme's secondary text color. A card configured under the old single entry keeps rendering exactly as it did - that entry became the group's fallback, so anything you had set still applies to all three until you override a field individually. The settings apply wherever those fields appear, both as standalone row columns and as lines inside a **Type** / **Name + type** / **Full name + type** cell.
- **The card is now suggested when you add by entity** - in *Add card → By entity*, picking an Annuals event sensor, one of Annuals' own calendars, or any other calendar offers the Annuals card among the suggestions, with a live preview. Each suggestion arrives configured for what was picked: one of Annuals' own calendars gives a card narrowed to that event type, any other calendar gives a card with that calendar already embedded. Entities the card has nothing to do with are not offered.
- **Two new row columns for an agenda-style list** (List view → Row columns). **Date block** writes the occurrence as three stacked lines - weekday, a large day number, month - the way a paper agenda prints its dates. It's a column of its own rather than a ninth *Date format*, so `{date}` in a custom text column and the Timeline keep rendering the single-line date; it always shows the real date, so *Say "Today"* doesn't apply to it. **Accent bar** is a colored bar the height of the row in that row's own icon color (Accent/Today/Soon), making today and the next few days visible before you read anything. Being ordinary columns, both can be placed, reordered and removed like every other one. The combined **Name + type** and **Full name + type** columns each get their own group in **Design**, with a row per line, so the name and type inside them can be styled without touching the standalone Name, Full name and Type columns. The Date block's three lines each get their own block in **Design**, under a *Date block* heading of their own - *Weekday*, *Day*, *Month* - independent of the Date entry, which belongs to the separate Date column. Sizes are relative to the card's own font size (0.75 / 1.5 / 0.75 when left empty); an empty color gives the weekday and month the theme's secondary text color and the day its primary one. The month's small-caps look is now the Uppercase toggle on its own row, on by default, so it can be switched off; the day has no such toggle, being a number. The Accent bar gets its own block in Design for its **Width** and **Color** - left empty it is 3px and each bar keeps its own row's icon color, and setting a color overrides all three categories with one fixed one.
- **Day, week and month separators** (List view → Row columns) - a line wherever consecutive rows fall on different days, in different weeks, or in different months, breaking a long list into blocks. Nothing is re-sorted or grouped: they only mark the boundaries the list order already has. Where a week starts is Home Assistant's own **First day of the week** – the setting on each viewer's profile page, next to Language and Time format – and on its default, *Language*, the week starts wherever the language the card is read in starts it: Monday across most of Europe, Sunday in the US. Each is its own block with a switch in its heading, and turning one on reveals its **Width**, **Style** (solid/dashed/dotted) and **Color** - the same three fields the Timeline's own line settings use. Left unset they default to 1px in the theme's text color, dotted for days, dashed for weeks and solid for months, so a list with more than one on reads as a hierarchy; a row that begins two boundaries at once gets only the coarser line. All three are off by default.

### Changed
- **Every CSS custom property now reads `--annuals-<scope>-<element>-<property>`** – **breaking for anyone theming the card**, and the one moment to do it while the card is still young. The old names had grown one at a time and no longer agreed with each other: an element’s color and its font sat in different namespaces (`--annuals-name-color` but `--annuals-row-name-size`), the layout appeared at the front in one name and in the middle in another (`--annuals-timeline-header-color` but `--annuals-vip-badge-timeline-color`), the same idea was spelled three ways (`-bg-color`, `-bg`, `-fg`), and some names were abbreviated while their neighbours were not (`fnt`, `sep`). Every name now carries one of four scopes – **card** (title, the no-events line, the background), **row** (everything in a list row), **timeline** (that layout’s own elements) and **status** (the four Accent/Today/Soon/Past colors both layouts share) – followed by the element spelled out in full and one of a fixed set of properties (`color`, `background-color`, `size`, `weight`, `style`, `transform`, `decoration`, `spacing`, `width`, `image`, `opacity`, `repeat`). So `--annuals-name-color` is `--annuals-row-name-color`, `--annuals-bg-image` is `--annuals-card-background-image`, `--annuals-today-color` is `--annuals-status-today-color`, and `--annuals-vip-badge-fg`/`--annuals-vip-badge-color` – the badge’s symbol and the disc behind it – are `--annuals-row-vip-badge-color` and `--annuals-row-vip-badge-background-color`, which say which is which. Nothing about a card’s stored configuration changed and no card looks different: only the names a theme or `card-mod` rule targets. The full table, with the release each name arrived in, is in the README under *Theming with CSS variables*.
- **Timeline line and Divider line moved into Design** - the axis and the rule between groups were configured on the *Timeline* tab, in two sections of their own, while every other thing that decides how the card looks lives under *Design*. They are Design blocks now, listed with the other timeline elements and built the same way: the name on an underlined heading with **Width**, **Style** and **Color** indented beneath it, exactly as *List (Details)* and *Details / More button* are. Nothing about how they render changed, and no config key moved.
- **Three redundant visibility switches are gone** (Layout → General → *Show / Hide*). **Past events** said exactly what a zero past window already says - *Time period → Days past* set to 0 - so there were two controls for one decision, sitting in different sections and free to disagree. **Today's events** and **Upcoming soon** hid precisely the events a card like this exists to show; neither had an arrangement it was good for, and "only today" already has its own switch under Time period. A card that had *Past events* off keeps its list: it is read as a zero past window on the next load, whatever *Days past* was set to. The other two are simply dropped. What remains are the three filters that actually narrow a list - **VIP only** and **Important only** on the left, **Open to-dos only** on the right.
- **The Layout section is six tabs instead of six differently-shaped ones** - it used to be Display, Fonts, Colors, Icons, Card background and Timeline, which cut across the card rather than along it: *Display* held the layout switch, the event filters and the row columns at once, while a single element's appearance was split between *Fonts* and *Colors*, so setting up one field meant two tabs. The tabs now read **General**, **List view**, **Timeline** on the first row and **Design**, **Highlight**, **Card background** on the second. *General* holds what neither layout owns - the layout switch and the event filters; *List view* holds the row columns with their separators and accent bar, and says so with a one-line note while the card is in the Timeline layout, the way the Timeline tab already did in reverse. *Design* replaces Fonts and Colors with **one block per element**: its name, then its color, then its size with Bold/Italic/Uppercase/Underline, then its letter spacing - so the whole appearance of a field is set in one place, and only the elements the card actually uses are listed. *Highlight* gains the whole **Icons** tab, since the icon is what the Default/Today/Soon categories paint. The **Accent bar**'s Width and Color moved into *Design* too - it is an element like any other, it just has a width where the rest have a font. **Tap action** and **Hold action** moved along with the rows they configure, from Settings → General into *List view*. No setting was removed or renamed, and nothing about a card's stored configuration changed - a dashboard written before this opens on the new tabs with every value where it was.
- **"Also color the text" became three switches per event type** - it started as one switch per icon category (Default/Today/Soon), back when the text could only follow an icon's color, then collapsed into a single card-wide switch once the color was resolved per row. Neither shape let a card say *which* part of a row a type's color should reach: it was icon and accent bar always, text for every type or none. Each event type now carries **Icon**, **Accent bar** and **Whole row** of its own under Layout → Design, so birthdays can color the whole row while holidays color only their bar. Old configs are read as they were written: any of the three original switches having been on means the card-wide one was on, and that in turn sets *Whole row* for every type - the reading that cannot silently take a setting away. A card that never touched them renders identically, since the defaults are the icon and the accent bar it already colored.
- **Compact starts with a shorter row** - switching on *Compact (no gaps, centered)* used to lay out Icon, Full name, Occurrence, Type, Countdown and Date, which read as a list of fields rather than the one continuous sentence the mode is for: the icon already says it's a birthday, and `Mar 3` next to `in 5 days` says the same thing twice. It now starts at `🎂 John Smith 42 in 5 days`. Both columns are still one click away in the columns list, and the absolute date stays reachable through *Tap countdown for date*. Only the starting arrangement changed - a card already switched to Compact keeps the columns it has.
- **An embedded calendar event's fields each get their own line** - the calendar's name, the time, the location and the description used to run together on one `·`-separated line in the **Name + type** / **Full name + type** / **Type** columns, which became an unbroken string as soon as more than one was switched on, and a description was long enough to swallow the short fields ahead of it. Each now sits on its own line, with **Time**, **Location** and **Description** led by an icon so they're legible without being read. Rows that aren't from an embedded calendar are unaffected - a holiday's `Holiday (Public) · US (Hawaii)` still reads as one line.

### Fixed
- **An icon name carrying a quote could inject markup into the card** – the row’s icon is written into the rendered HTML, and its value is not always a plain `mdi:name`: it comes from the icon field, from the icon column of an imported CSV, or from another integration’s entity attribute. A value containing a double quote closed the attribute early, and anything after it was parsed as markup rather than shown as text – markup that runs, in the dashboard’s own context. Importing a CSV from a source you do not control was the realistic way in. Icon names are now escaped wherever they are written into markup, in the row, on the VIP and Important badges and on the editor’s embedded-calendar rows.
- **Reminder blueprint: a stray comma in “Remind this many days before” added a reminder you did not ask for** – the field is free text, and anything in it that was not a number became 0, which means “on the day itself”. So “7,1,0,” with a trailing comma quietly reminded twice on the day, and clearing the field entirely meant “remind on the day” rather than “never remind”. Entries that are not numbers are now dropped instead.
- **Reminder blueprint: the notification’s “Done” button did nothing when the title contained a “|”** – the button carries the to-do list and the item text in one string, separated by that character, and splitting it back apart stopped at the first one it found. A title written with a pipe in it therefore handed back a shortened item text, which matched nothing on the list, so tapping Done silently left the item open. Titles are now recovered whole, pipes and all.
- **The card counted from the wrong day when Home Assistant’s time zone differed from the machine’s** – every countdown, every “today”/“tomorrow”, the to-do matching and the automatic clean-up of past one-time events took “today” from the operating system rather than from the time zone set under Settings. The two are usually the same, and then nothing changes; where they are not, everything was a day out for the offset between them – and worst right after the nightly refresh that rolls the countdowns over, because that refresh is scheduled in Home Assistant’s own zone. A one-time event could be removed a day early on the same mismatch. The calendar entity had always read the right one; now the sensors agree with it.
- **A lunar-calendar holiday could report last year’s date** – the holiday data is cached per country, region, category and year, but the library’s calendar object quietly loads extra years into itself when a date outside its own is looked up. Since the cache is shared, one such lookup left every later reader holding years it never asked for, and the date resolver takes the earliest match – so a holiday whose date is estimated rather than fixed (Eid, Ashura, and the rest of the Hijri calendar) could answer with the previous year’s occurrence, a fortnight or more off. The cached calendar is now a snapshot that cannot grow, so the question cannot arise again.
- **Re-submitting a CSV import without picking the file again failed with “Unknown error occurred”** – an uploaded file is deleted as soon as it has been read, so a second submit of the same form – after a “no valid rows” message, or after a restart – handed the import an id that no longer existed. Both CSV steps (events and holiday translations) now report it as an unreadable file, the way the ICS and vCard steps already did.
- **The editor said “Suffix (Type)” in every language** – the row asked for a translation key left behind by the rename of the *Subtitle* column to *Type*, which no language has carried since. It fell through to its hardcoded English word every time, so the German editor read `Suffix (Type)` instead of `Suffix (Typ)`. It asks for the key the Type column actually uses now.
- **Past events' settings had no effect on the Timeline** - the timeline worked out which status an event belongs to from its countdown, but a past event's distance lives in `daysSince`; its `days` already points at next year's occurrence and is never negative. So the Past status matched nothing there and its colours and animation were quietly ignored. It now uses the same test the axis itself does.
- **A status' Entry text color switch did nothing** - it shared its key with the list's *Whole text color*, so two switches carried the same name. Only the first was ever wired, and that one is hidden in the Timeline layout: the visible switch had no handler at all, and every other switch's handler read the hidden one's state back into the config. The timeline's text has a switch of its own now, as its icon color already did.
- **Switching a status' Icon animation off turned itself back on** - the reading that carries an older card's Today or Soon animation onto the new switch runs on every config read, not once, so a status whose switch had just been cleared looked untouched again and had it set straight back. It now leaves a status alone once it carries a decision of its own.
- **A block's first row sat too tight under its heading when the row above it was hidden** - the rule that pulls the first setting up against its divider keys off the DOM, so a hidden first row left the next one lifted by its own negative margin. Visible in the Timeline layout's **Icon** block, whose Color is hidden there. The first *visible* row is now the one that sits flush, in every block.
- **The icon animation had no control left in the Timeline layout** - the animation reaches the timeline's own header and Details-list glyphs as much as it does a list row's icon, but moving the default into the Icon column's Design block tied it to a column the timeline does not have, and the per-status ones were hidden there along with their colors. Both are back in the Timeline layout. Their **Color** stays list-only, which is the split that was always intended: the timeline colors those glyphs from the event type, the animation is layout-agnostic. In the Timeline layout the Icon block is also listed where it belongs, between *Header* and *Tooltip*, rather than where a row column would have put it.
- **Two rows in the editor had no tooltip at all** - a line's **Style** and every font block's **Letter spacing** were the only fields with no "i" beside them. Both have one now.
- **Design and the event types talked about "rows" in the Timeline layout too** - *Design* holds the timeline's own elements (Header, Tooltip, List (Details), Details / More button, and now the two lines) alongside the row ones, so its block description says "this part of the card" rather than "this part of the row". The per-type colors and the per-calendar ones paint the timeline's dots as well as the list's rows, which their tooltips now say instead of naming only rows.
- **Settings that apply to both layouts talked about "rows"** - *Merge holidays shared by several countries* and *Multi-day events* live under Settings and hold for the Timeline just as much, where an event is a dot and an entry rather than a row. Both now say "entry".
- **The Accent bar's Design color beat everything instead of being the default** - it was applied as one fixed color for every bar, so an event type's color and a status' color both had no effect on the bar while it was set. It is now the bottom of the same chain the icon follows: the card's own default, then the **Design** block for the column, then the **event type** where *Color rows by event type* is on, then the row's **status**. The bar reads one resolved value per row, the way the icon already did.
- **Rows with no status behaved as though they were Today** - an ordinary row looked its override settings up under a status it does not have and fell through to Today's defaults, which override everything. So on a card with per-type colors, plain rows kept the Design color where they should have taken their event type's. A row with no status now overrides nothing, which is what makes it the end of the chain.
- **The Timeline's Badge color only reached its axis dots** - the Timeline draws each badge in three places (the axis dot, the header row, and the expandable Details list), and only the dot read the Timeline's own *Badge color* field. The header and the Details list read the **List** layout's field instead - which the editor does not offer while the Timeline layout is selected, so that colour had no way to be set at all: changing *Badge color* moved the dot and left the two textual views where they were. All three now read the Timeline's field, which is the one-field-per-layout arrangement the editor has always presented.
- **The VIP badge previewed white and rendered red** - on the axis the VIP star fell back to white while the same star in the Details list fell back to the theme's red, so one field had two defaults and the editor's colour preview could only be right about one of them. Both are the theme's red now, and the swatch previews it. A white star also disappeared entirely on a light theme, which red does not.
- **"Only next event day" could empty the card completely** - it kept whichever events shared the smallest countdown, and a row already behind us has the smallest of all: a multi-day trip's start row once the trip has begun, or an external calendar event inside the past-events window. That row won, took every other event off the card with it, and was then dropped again by the past-event settings - leaving nothing at all. It now picks the soonest day that is today or later, falling back to the soonest day there is only when every remaining event is in the past, so that card shows that day instead of emptying itself. Events sharing the chosen day are all kept, as before.
- **A multi-day event already under way was shown as starting today** - a trip that began on the 16th kept its start row on today's date, in both layouts, and the row read "today" with it. The card worked out which day a row was about by adding the sensor's countdown to today, and that countdown deliberately holds at 0 for as long as a multi-day event runs (so automations reminding "in 7, 1, 0 days" never see a negative number) - which put every day of the trip on the day it was being looked at. Rows now take the day from the sensor's own `next_date`, so the start row stays on the start date and says how long ago that was; the timeline's sentence switches to the past tense with it ("Vacation Mallorca was 2 days ago (Aug 16)" instead of "is today"). Each row now counts from the day it is about, which also puts it under the card's own past-event settings: a card showing no past events drops the start row once the trip has begun, so *Only the first day* stops listing a trip while it runs, while *First and last day* keeps it through its end row and *Every day* through the day it is on. Recently-past rows of ordinary events are unaffected: `next_date` has already moved on to next year's occurrence there, so those keep counting back from today as before. The sensor's own state is unchanged - it still holds at 0 while the event runs, which is what the blueprint reads.
- **"Open to-dos only" emptied out the embedded calendars** - with the filter on, every event from an [external calendar](#external-calendars) disappeared along with the Annuals events that had nothing left to do. An external event can never carry a to-do the card can see in the first place, so it was being dropped by a test it had no way of passing. It now stays in the list, exactly the way *VIP only* and *Important only* already left it alone - those three filters narrow Annuals' own events and leave the embedded calendars to the day-window settings.
- **Switching off "Show icon" for one category pulled those rows out of line** - with the icon hidden for, say, Default but not for Today and Soon, the affected rows lost their icon cell from the shared column grid, so every field behind it slid one column to the left and picked up a different left padding on top. The icon column now keeps its place and its width for those rows and only the icon itself is hidden, so they line up with the rows that still have one. Turning the icon off for *all three* categories still reclaims the column entirely, since there is then nothing left to line up with - and Compact, which is a running sentence rather than a table, still closes each row up on its own.
- **The badge's Background color row stayed visible with the background switched off** - it now appears only while *Show background* is on, since it has nothing to color otherwise.
- **Bold, Italic and Uppercase on Type did nothing for an embedded calendar event** - that row's Type cell is built from the calendar's own lines, whose styling defaulted to `normal`/`none` and so overrode whatever Type was set to. Size, letter spacing and underline appeared to work because the first two inherit and an ancestor's underline cannot be switched off by a descendant. Those lines now inherit Type, and the External calendar fields entries still override it whenever they are actually set.
- **The Design group headings stayed behind in the Timeline layout** - *Name + type*, *Full name + type* and *Date block* name list-layout columns, so their rows were correctly hidden in the timeline layout, but the headings above them were not and were left standing with nothing underneath.
- **The line color fields showed an English-only placeholder naming a color they no longer use** - the Timeline line, Divider line, Accent bar and the three separators suggested `var(--divider-color)` (or `var(--primary-color)`) as an example, hardcoded in English. All six now use the same translated placeholder every other color field has.
- **The Timeline's axis and divider lines were barely visible** - both defaulted to the theme's `--divider-color`, which carries a 12% alpha of its own, so the lines rendered at a twelfth of their apparent color and their swatches could not match them. Both now default to the theme's secondary text color at full strength.
- **No field is dimmed with `opacity` any more** - Type (0.6), Countdown (0.8) and the "no events" placeholder (0.6) were faded that way, which dimmed any color chosen for them along with everything else, so they could never match their own swatch. Every field now takes the theme's own colors at full strength. The only remaining uses of `opacity` on the card are the two where it is the point: the background image's own opacity setting and the Flash icon animation.
- **Color swatches did not show the color the field actually renders in** - three separate causes. The browser draws its own grey frame and padding inside a native color input, which at 28-36px took up enough of the square to visibly mute it, so an Icons swatch read as a duller red than the icon beside it; the square is now filled edge to edge. The **Date** and **Calendar fields** rows in Layout → Design had no default of their own to fall back on, so they previewed white; Date now shows the theme's primary text color, and the three External calendar fields rows its secondary one. And *every* swatch could come up white when the editor was opened, because the preview resolved theme variables against an element that was not yet in the page - it now resolves against the document, so the squares are right from the first render rather than only after the next state update.
- **"Value UK is not a valid option" when importing United Kingdom holidays** - the country picker offered both `GB` and the `holidays` library's own `UK` alias for the same country, but Home Assistant's country selector only accepts official ISO 3166-1 alpha-2 codes, so the `UK` entry could be picked and never submitted. The picker now only offers codes the selector actually accepts: the United Kingdom is `GB`, with the same four subdivisions. Kosovo (`XK`) drops out for the same reason - it has no official two-letter code - and its holidays are no longer reachable through this form.

## v3.0.0

### Added
- **One-time events can span several days** - a holiday trip, a conference, a hospital stay. Add an **End date** and the event runs from its start to that day inclusive; leave it empty and nothing changes. The countdown counts down to the start and then holds at 0 for the whole time the event runs instead of going negative, with `in_progress` telling the two apart. It's removed after its *last* day rather than its first, shows on the calendar entity as one all-day event covering the range, and carries `end_date`, `days_until_end`, `duration_days`, `in_progress` and `reminder_message_end` as attributes. The **card** lists it as its first day, its last day, both, or one row per day (Events → *Multi-day events*), dropping days already past. The **reminder blueprint** counts down to the start, the end, or both (Multi-day events → *Remind about*) - the end gets its own to-do item, so ticking off the departure doesn't swallow the reminder about coming home. The event CSV gains an `end_date` column; a CSV written before this imports unchanged.
- **School holidays are imported as whole breaks** - a break used to become a single event on the first day the school calendar happened to list. It is now recognised as the break it is, and the import asks which parts of it you want: its **first day**, its **last day**, and/or **every day** as one event each, in any combination. Each part says which it is, in Home Assistant's own language at the time of the import: `Herbstferien (Beginn)`, `Herbstferien (Ende)`, `Herbstferien (Tag 3)`. The wording is fixed when the entry is created, so changing the server language later doesn't rename events you already have. School calendars list school days only, so the real break starts and ends outside them: the first day is found by counting back over the weekend and any adjacent public holidays, and the last day by counting forward the same way. A Bavarian autumn break listed Mon Nov 2 – Fri Nov 6 is therefore imported as Sat Oct 31 to Sun Nov 8. Weekends are taken from the country itself, so Israel's Friday/Saturday works the same way as Germany's Saturday/Sunday. Only offered for countries that actually have such breaks; nothing changes for the statutory categories.
- **Your own name for any holiday, in any of the 15 languages** - each imported holiday keeps the name it was imported under, and you can now add a translation for every other language, or correct the imported name itself. Configure a holiday and pick **Holiday names**. Useful where the `holidays` library has no translation for your language, and where two regions call the same day different things (see the note under *Merging* below).

### Added
- **Automation blueprint: "Annuals - Upcoming Event Reminders"** (`blueprints/automation/annuals/annual_reminders.yaml`) - target specific events or every event of a chosen type, filter by VIP and/or Important (each independently "must be" or "must NOT be", combined as AND or OR when both are active), remind at multiple "days before" thresholds in one automation. ### Fixed
- **New Year's Day (and any other holiday whose observed shift can cross a calendar-year boundary) could show the wrong "observed" date** - the `holidays` library backs a Jan-1-falls-on-Saturday shift into the *previous* December, which landed in that year's own data alongside its unrelated literal Jan 1 - naively pairing "the first observed-looking entry found that year" with the literal date could attribute a future year's shift to the current year (or miss the current year's real shift entirely). Observed-date resolution now only pairs a shift with a literal date if they're within a few days of each other, checking neighboring years instead of assuming everything relevant is in the requested year's own data.
- **Holiday import could permanently freeze a "(observed)"/"(estimated)" suffix into the entity's name** - if a statutory holiday's shifted date fell chronologically *before* its own real date in the year it was imported, the import picked that shifted occurrence's name for the entity - and since the name is stored once and never recomputed, it stayed wrong in every future year even though the resolved date itself was always correct. Import now always prefers the plain (unsuffixed) occurrence regardless of date order, and existing holiday entities self-heal on next reload/restart.
- **Several holiday categories showed up untranslated** (e.g. Switzerland's "de_facto") in both the dashboard card's category filter and the native "Import holidays" category checklist - the previous category list was incomplete (16 of the `holidays` library's actual 26 category values). These columns now match the combined columns' layout behavior, so custom row-column combinations align like a table again, same as the built-in layout always has.
- New Row columns added via the "+" button got a random id suffix (e.g. `last_name-q5b9zq`) even when only one of that type existed. Only actual duplicates now get a numbered suffix (`-2`, `-3`, ...); the first of each type keeps a clean, readable id (e.g. `last_name`).
